# 消息指代（reference）—— 调研与设计

> 状态：**第一期已落地并验收**（2026-10-15）→ 见 [`REPORT.md`](REPORT.md)
> 本文是实现的唯一依据；第二、三期尚未开工。

---

## 0. 目标与非目标

**目标**：让机器人对每一条收到的消息，明确知道「谁说的 / 说给谁 / 在回应什么 / 提到了谁」。

**非目标（本期不做）**：
- ❌ 代词消解（「他」「楼上」指谁）—— 第三期，可选开关
- ❌ 模仿任何人的说话方式
- ❌ 改变「发不发、发什么」的任何决策逻辑

**第一期不改变任何群内可见行为。** 它只让模型看得更清楚。

---

## 1. 三条不可违反的原则

### 1.1 QQ 号是唯一真身，名字只是观测值

群名片与 QQ 昵称**随时可改**，因此：

- **uid 是唯一键；`card` / `nickname` 是挂在 uid 上的、带时间戳的观测**，不是标识；
- **禁止**任何「名字 → uid」的静态映射表（改名即失效，且旧名字从此查不到）；
- 名册里同一 uid 可以有多条历史名字，它们**都是事实**（在不同时间成立）。

### 1.2 渲染历史消息用「当时的名字」

每条消息的 `sender` 自带**发送当时的** `card` / `nickname` 快照。
所以历史上下文里显示的名字天然准确，**不需要、也不应该**回查名册用「现在的名字」覆盖它。

```
消息事件自带快照  →  历史上下文准确   （用当时的名字）
名册的 current    →  只在需要「他现在叫什么」时用   （如群友印象）
```

### 1.3 反查结果永不写回名册

「名字 → uid」是**模糊、可能多义、可能查不到**的推断。
一旦把推断结果写进名册，它就变成了「事实」，后续会自我强化、越错越离谱。

**硬规则**：`resolve()` 是只读的纯函数，输出只能用于当前这一轮的渲染/提示，
**绝不允许回写 `roster.json`**。名册的写入只有两个来源：
1. 消息事件里的 `sender` 字段（权威）
2. 人工显式登记的别名（带 `source: "manual"` 标记）

## 2. 调研结论（全部实测取证）

### 2.1 每条群消息事件免费带的字段

从 NapCat fileLog 抽到的真实原文（群 284517232）：

```json
{
  "post_type": "message", "message_type": "group", "sub_type": "normal",
  "self_id": 2668851638, "user_id": 1305489180, "time": 1792028836,
  "message_id": 688686492, "message_seq": 688686492,
  "real_id": 688686492, "real_seq": "94592",
  "group_id": 284517232, "group_name": "碧油鸡乐土（转正版）",
  "sender": { "user_id": 1305489180, "nickname": "UC", "card": "", "role": "member" },
  "raw_message": "…", "font": 14, "message": "…"
}
```

**三个必须记住的事实**：

1. `card` 字段**每条都有，但经常是空串**（该用户没设群名片）→ 回退链必须 `card → nickname → uid`；
2. `role` 免费带着（member / admin / owner）；
3. `message_seq` / `real_seq` 也在。

### 2.2 引用的硬限制（决定了架构）

`replyElement` 解码后只产出 `{ type: "reply", data: { id: <msgId> } }`——
**只有 message_id，没有被引用者的 uid，也没有原文。**

⇒ **必须自建「message_id → 消息元数据」索引。**
项目已有先例：`scripts/image_cache.py` 就是为识图做这件事的，但**只用在图片上**。

### 2.3 需要时才拉的补充 API（本期不用）

`get_group_member_info` 可拿到 `sex/age/area/level/qq_level/join_time/title`。
本期不用——消息事件里的字段已经够，少一次 WS 往返。

|---|---|---|---|
| ① | `reverse_bot.py:349` | `re.sub(r'\[CQ:\w+,[^\]]*\]', '', raw_message)` | 引用、@ 全被剥掉 |
| ② | `reverse_bot.py:376` | `sender.get("nickname")` | 取 QQ 昵称，**`card` 被无视** |

| ⑤ | `decision_engine.py:441` | `f"- {uid}: {desc}"` | 画像用**裸 QQ 号**，与上下文里的名字无法关联 |

**没有任何办法知道这是同一个人**。整块「群友印象」对具体人的推理等于失效。

## 4. 数据模型

### 4.1 消息索引（内存，每群环形）

```python
{
  "message_id": "688686492",
  "uid": "1305489180",
  "card": "",              # 【当时的】群名片快照
  "nickname": "UC",        # 【当时的】QQ 昵称快照
  "role": "member",
  "text": "别说了",         # 剥 CQ 后的纯文本
  "at": ["10001"],     # @ 的 uid 列表
  "reply_id": "688686490",  # 引用的 message_id（无则空串）
  "ts": 1792028836.0,
}
```

**存结构化字段，不存渲染好的字符串**——以后想改渲染格式，不必重建缓冲。

窗口：**每群 200 条**（一条约 200 B → 40 KB/群，可忽略）。
超出窗口的引用 → 降级文案，**不编造原文**。

### 4.2 群成员名册（持久化，uid 为键）

```json
{
  "version": 1,
  "updated_at": "2026-10-15T10:30:00+08:00",
  "users": {
    "10001": {
      "nickname": { "value": "往事随风", "seen_at": 1792028836 },
      "groups": {
        "284517232": {
          "cards": [
            { "value": "阿强",       "seen_at": 1791500000 },
            { "value": "阿强[加班]", "seen_at": 1792028836 }
          ],
          "current_card": "阿强[加班]",
          "aliases": [],
          "first_seen": 1791000000,
          "last_seen": 1792028836,
          "msg_count": 431
        }
      }
    }
  }
}
```

**设计要点**：

- 唯一键是 **uid**；`nickname` 是全局属性，`cards` 是**群级**属性（同一个人在不同群不同名片）；
- `cards` 是**观测序列**，同值不重复追加（只刷新 `seen_at`），只保留最近 N 个不同值；
- `current_card` / `nickname` 是冗余的「最后一次观测」，渲染用，**不是标识**；
- `aliases` 必须带来源标记；**只有 `source: "manual"` 的别名才允许参与确定性解析**。

### 4.3 两个方向的查询能力（不对称，必须分清）

| 方向 | 函数 | 性质 | 用途 |
|---|---|---|---|
| uid → 名字 | `display_of(uid, gid)` | **确定性**，必成功（回退到 uid） | 渲染、画像注入 |
| 名字 → uid | `resolve(name, gid)` | **模糊**，可能 0 / 1 / 多个 | 仅本轮提示，**绝不回写** |

## 5. 上下文渲染格式

**现状**：`[UC]: 别说了`

**改为**：

```
[UC] 今天天气不错
[UC@阿强] 别说了
[UC 回复阿强「我明天可能来不了」] 你说得对
[UC 回复某条消息] 你说得对          ← 超出缓存窗口，降级不编造
```

**为什么用显式中文而不是 `→` `↩` 这类符号**：中文模型对「回复」「@」的理解远好于符号。

### ⚠️ 5.1 必须同步改输出侧（本改动唯一碰输出路径的地方）

`decision_engine.py:77` 有「昵称前缀剥离」——防止 LLM 学着上下文格式输出 `[昵称]: 内容`。
**新增的格式必须同样可剥离**，否则机器人会开始输出 `[A@B] …`。

引用原文**截断 40 字**，否则长引用会撑爆上下文。

## 7. 分期

| 期 | 内容 | 风险 | 群内可见变化 |
|---|---|---|---|
| **一** | 捕获 `card`/`role`/`at`/`reply` + 消息索引 + 渲染指代 + 画像用展示名 | 低 | **零** |
| **二** | 名册持久化（历史名片、别名、互动图） | 低 | 零 |
| **三** | 代词消解（「他」「楼上」），可选开关、**必须给依据**、只写日志 | 中 | 零 |

第三期后置的理由：确定性部分做完后，「他/那个」的歧义**本来就少了一大半**——
大部分指代是 @ 和引用，而那些是确定性的。

## 8. 验收方式（不需要发任何测试消息）

**NapCat fileLog 里有完整的一手原始事件**（2026-10-15 单文件 502 KB / 209 条 sender 记录）。

1. **合成用例**：含 @ / 引用 / 改名片 / 无名片 / 超窗引用，断言注解输出；
2. **真实回放**：从 fileLog 抽真实事件回放注解层——最有说服力且可重复；
3. **离线断言**：上下文里不出现裸 uid；@ 目标不丢失；引用能解出原作者；
4. **回归**：`python -c "import reverse_bot; print('OK')"`；
5. **输出侧**：断言扩展后的剥离正则能吃掉 `[A@B] …` 形态的模型输出。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型模仿新格式 | 同步扩展输出侧剥离正则（**唯一必动的输出路径**） |
| 上下文变长 | 引用原文截断 40 字；上下文条数不变 |
| 引用超出窗口 | 降级文案，不编造 |
| `card` 常年为空 | 回退链 `card → nickname → uid`，绝不渲染空名 |
| 改名导致认知错位 | 历史消息用当时快照；名册只用于「现在叫什么」 |
| 名册无限增长 | `cards` 只留最近 N 个不同值；名册有保留期 |
| 隐私等级上升（聚合数据比散话敏感） | 进 `.gitignore`；保留期可配；提供删除出口 |
| 推断污染名册 | §1.3 硬规则：`resolve()` 输出永不回写 |
