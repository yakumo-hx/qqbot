## 4. 真实数据暴露并修掉的一个缺陷

回放时发现有一行漏出了原始 CQ 码：

```
[UC] [CQ:face,id=474,raw={"faceIndex":474&#44;...
```

**根因**：NapCat 的 `CQ:face` 带超长 `raw={...}` 参数，日志里被截断成**没有闭合 `]`** 的样子，
严格正则匹配不到 → 整段 CQ 原文漏进模型上下文。

生产环境 WS 消息是完整的，所以这不是线上故障；但它是一个真实的脆弱点。
**已修**：`strip_cq` 改为两遍剥离（先剥闭合的，再补一刀剥未闭合的），
`decision_engine._CQ_CODE` 同步加固。回放复验：泄漏从 1 行降到 **0 行**。

回归用例：`test_strips_unterminated_cq`。

## 6.5 试运行配置（2026-10-15 12:30）

按用户要求，先在**单个群**上试运行：


设计与语义：

- **`groups` 为空数组 → 所有群启用**；非空 → 仅列出的群启用；
- **配置写坏时保守关闭**（`groups` 不是数组 → 一律 False）。
  刻意 fail-closed：不能把「配置写错了」变成「全群开启」；
- 不走 `group_features.json` / `_FEATURE_KEYS`：那是全项目共用的早退闸门，
  改它会影响所有群的消息路由；用功能自己的配置收窄影响面更安全，
  也与 `config/interaction_menu.json` 的 `groups` 先例一致；
- **未列出的群行为完全不变**：不注解 → `ref=None` → 渲染回退旧格式；
  名册里也没有它们的观测记录，`display_of()` 回退到 uid，画像输出与改动前逐字相同。

### 试运行暴露的一个实现缺陷（已修，待重启生效）

`data/roster.json` **一直不生成**。根因：`observe()` 只写内存，**没有任何地方调用 `save()`** ——
`flush_if_due()` 从未被触发，名册重启即丢。渲染不受影响（内存里也有），所以只影响持久性。

修法：
1. `observe()` 在**锁外**调用 `save(force=False)`（持锁调用会死锁——`save` 自己也要取锁），
   受 `roster_flush_seconds` 节流；
2. `save()` 失败时**不再清 `_dirty`**（否则一次写盘失败会让脏数据永远丢掉），
   但仍推进 `_last_flush` 避免每条消息都重试；
3. `main()` 的 finally 里 `flush(force=True)`，退出前兜底；
4. 补两条回归测试（`test_observe_alone_persists`、`test_first_observe_persists_even_with_throttle`）。

顺带修正一条**因修复而失效**的旧断言：`test_persist_and_reload` 原本断言 `save(force=True)` 返回 True，
但 observe 现在已自动落盘、此时无脏数据，返回 False 才是正确行为。

### 修复生效（2026-10-15 14:19 重启后）

```
data/roster.json  存在  512B  mtime=14:19:48   ← 重启后 34 秒落盘
14:19:14  机器人服务端 v2.5.0 启动（新进程）
```

名册结构核对通过：

```json
"***0590": {
  "nickname": { "value": "多喝热水", "seen_at": … },
  "groups": { "284517232": {
      "current_card": "芽1为真",
      "cards": [{"value": "芽1为真", "seen_at": …}],
      "role": "admin", "msg_count": 1 } }
}
```

- ✅ 键是纯数字 uid（不是名字）
- ✅ cards 是带 `seen_at` 的观测数组（历史名片）
- ✅ 没有「名字 → uid」的静态映射表
- ✅ 昵称（全局）与名片（群级）分开存

**闭环验证**：名册里 uid `***0590` 的 `current_card` 是「芽1为真」，
日志里同一时刻渲染的就是 `[指代] [芽1为真] 查了一下，才发是像泡一样的东西`。

### 第二个缺陷：节流饥饿（同日修复）

首次修复后仍有一个时序缺口：`save()` 只在 `new_info` 为真时被调用。

**故障场景**：新面孔出现在节流窗口（300s）内被挡下 → 此后群里再没有新人 →
那份脏数据**永远留在内存里**，节流到期也没有任何东西去触发它，进程被硬杀即丢。
（实测征状：名册 mtime 停在 14:19:48，而期间已出现新面孔 `[IJS大分部队]`。）

**修法**：`observe()` 每次都试一次 `save(force=False)`（`save` 内部自己判脏与节流，代价可忽略），
而不是只在 `new_info` 时试。补回归测试 `test_pending_save_lands_when_throttle_expires`（用假时钟推进节流）。

单测：**49 项全通过**。

**这一项同样需要下次重启才生效**（当前进程跑的是上一版代码；影响仅限于「硬杀时可能丢一小段观测」，
优雅退出有 `flush(force=True)` 兜底）。
