你将在 Windows 工作目录 E:\QQbot 中，对现有个人 QQ 机器人进行 LLBot 通道的可行性与兼容性试验。

你的任务是“受控测试、保留证据、随时可回滚”，不是直接把生产环境迁移到 LLBot，也不是重构现有机器人。

==================================================
一、目标与约束
==================================================

目标按顺序分为两阶段：

A. LLBot PMHQ 有头模式：
   验证现有 OneBot 11 业务能否跑在 LLBot 上。

B. LLBot 纯协议无头模式：
   在阶段 A 核心兼容性通过后，只切换无头模式，验证不依赖 QQ 客户端时的登录、恢复与业务表现。

硬约束：

1. 不使用 QQ 官方 Bot 开放平台，不使用带官方机器人标识的账号。
2. 不采用“手工替换官方 QQ 文件”的旧安装路线。
3. 不测试 DSH、OpenClaw、AstrBot、MaiBot、Lagrange NativeAPI 等其他路线。
4. 不让 NapCat、LLBot 有头、LLBot 无头同时登录同一个 QQ 账号。
5. 绝不操作用户个人 QQ，只处理专用机器人账号及明确属于测试协议的进程。
6. 禁止 taskkill /im QQ.exe、Stop-Process -Name QQ 等按全局进程名操作。
7. 不删除或覆盖现有 NapCat、生产配置、私聊永久数据和历史日志。
8. 不重写现有人格、记忆、ConversationRuntime、模型池或群聊业务。
9. 不做 git commit、tag、push，不修改 git 配置。
10. 官方文档已明确警告“无头模式有掉线风险，号体质不佳的慎用”，不得预设无头模式更稳定。

LLBot 官方来源：
- 仓库：https://github.com/LLOneBot/LuckyLilliaBot
- 介绍：https://luckylillia.com/guide/introduction
- 安装：https://luckylillia.com/guide/choice_install
- 配置：https://luckylillia.com/guide/config

只使用上述官方仓库 Releases 和官方文档。不要使用旧 LLOneBot 教程、第三方镜像或来历不明的整合包。

==================================================
二、允许写入的范围
==================================================

可以：

1. 在 E:\QQbot-trials\ 下安装 LLBot、放置测试副本和测试运行数据。
2. 在 E:\QQbot\qq_native_re\findings\llbot_trial\ 下写测试脚本、测试矩阵、日志摘要和最终报告。
3. 在 E:\QQbot\qq_native_re\patches\llbot_trial_<timestamp>\ 下保存备份。
4. 为测试创建隔离配置、隔离 data_dir、测试用 OneBot 接收端和探针。

默认不得修改生产 Python 业务文件。若发现必须做适配才能继续：

- 先记录具体不兼容点；
- 不要顺手重构；
- 只在测试副本中做最小适配；
- 清楚标注 patch、原因和回滚方式；
- 不直接污染生产工作区。

PowerShell 版本不支持 &&，使用分号 ;。需要运行现有 Python 时使用项目 venv，并设置 PYTHONIOENCODING=utf-8。

   - 启用的群；

4. 从现有日志提取 NapCat 对照基线：
   - 统计时间范围；

7. 写 ROLLBACK.md：
   - 如何停止 LLBot；

   - 如何恢复 NapCat；

备份未完成、回滚路径不明确，不得进入真实账号测试。

==================================================
四、测试隔离与生产安全
==================================================

1. LLBot 安装到独立目录，不覆盖 NapCat。
2. 有头模式使用原版 64 位 NTQQ，按 LLBot 文档由 LLBot 拉起 QQ。
3. 预检 LLBot 是否会读写用户个人 QQ 的默认数据目录。
   如果无法隔离机器人账号与个人 QQ 数据，停止并报告，不得冒险试验。
4. LLBot 初期只启用：
   - 当前测试所需模式；
   - OneBot 11；
   - 本地反向 WebSocket。
5. Milky、Satori、额外 HTTP 服务、非必要插件先关闭。
6. onlyLocalhost 保持 true；WebUI、HTTP、WS 不向公网开放。
7. AccessToken 只写入本地测试配置，不进入报告。
8. 测试 WS 先用独立端口和隔离接收端，不直接抢占生产 8080/8081。
9. 私聊测试使用隔离 data_dir，不读写生产 data/private 的永久会话。
10. 主动消息默认关闭；只向用户明确批准的测试群和私聊白名单用户发消息。
11. 不向全部已知群广播，不做戳一戳、表情回应、撤回等可见操作，除非用户明确批准目标。
12. 停产切换、人工扫码、第一条真实群消息如需用户操作，明确告知用户。
    无法人工完成时标记 BLOCKED，不要假装测试通过。

==================================================
五、阶段 A：LLBot 有头模式
==================================================

先确认：

- NapCat 已完全停止机器人账号登录；
- LLBot 有头模式使用独立数据；
- 当前没有第二个客户端登录同一机器人账号；
- 用户个人 QQ 未受影响。

记录 LLBot 版本、release URL、安装包哈希、QQ 版本、PMHQ 配置和启动时间。

A1. 协议与连接测试：

- OneBot 反向 WS 能否连接；
- heartbeat 是否正常；
- get_login_info；
- get_status；
- 群消息和私聊消息事件；
- sender、message_id、raw_message、message 字段；
- messageFormat 与现有 CQ/raw_message 解析的兼容性；
- echo 回执、retcode、message_id；
- 两个独立 WS 通道能否同时工作且互不覆盖。

A2. 核心 action 测试：

必须逐项记录 PASS / FAIL / BLOCKED / NOT_SUPPORTED：

- send_private_msg
- send_group_msg
- get_friend_msg_history
- get_group_msg_history
- get_msg
- 图片接收与下载
- 图片发送
- 回复与 @ 消息
- get_group_member_list
- 当前项目实际使用的其他关键 action

扩展项单独列出，不因非关键扩展失败而误判核心失败：
- set_msg_emoji_like
- group poke
- 群公告相关接口
- 文件相关接口

不要假设 LLBot 与 NapCat 的扩展 action、message_id 或历史消息顺序完全一致。

A3. 顺序与回执：

- 连续文本消息是否乱序；
- 图片后紧跟文字是否乱序；
- WS 断开后是否重复补报；
- 重连后历史补拉是否重复；
- action 超时时能否区分 failed 与 unknown；
- unknown 不得自动重发；
- 发送回执中的 message_id 是否可用于落盘；
- 两条 WS 是否发生交叉回应或相互清理。

A4. 故障注入：

每次只改变一个变量：

- 停止并恢复测试 WS 服务端；
- 重启 Python 测试接收端；
- 通过 LLBot 正常方式重启协议端；
- 模拟 action 超时；
- 测试大图片或较大 payload，但不发送危险或超大文件；
- 如可安全模拟，再测试断网恢复。

记录协议端是否在线、WS 是否在线、QQ 是否在线，不能把三者混为一个“连接正常”。

A5. 现有业务验证：

优先使用测试副本和隔离数据。

只有在核心探针通过后，才考虑接入现有 reverse_bot/private_bot 测试副本，并限制到指定测试群与私聊白名单。

验证：
- 群聊被动回复；
- 私聊结构化多气泡；
- revision 打断；
- 主动任务竞争；
- 私聊重连历史补拉；
- 每气泡回执与落盘；
- 图片识图链路；
- 模型池无需因通道变化而修改。

若无法安全隔离生产配置，不要直接改生产来强行完成；记录阻塞原因和最小适配需求。

阶段 A 任一核心私聊能力无法验证时，不得声称“完全兼容”。

==================================================
六、阶段 B：LLBot 纯协议无头模式
==================================================

只有阶段 A 核心 API 基本通过后才进入。

1. 停止有头模式及对应 QQ，确认同账号没有第二登录端。
2. 备份有头模式配置和关键状态。
3. 尽量保持 LLBot 版本、OneBot 配置、测试脚本和业务配置不变。
4. 只将 headless 切换为 true，并记录必要登录配置差异。
5. 不删除有头数据，不清空账号状态，不并行运行两种模式。
6. 完整重跑 A1～A5 的核心测试。
7. 单独记录：
   - 首次扫码；
   - 快速登录；
   - 登录失效；
   - 设备验证；
   - KickedOffLine；
   - 静默离线；
   - 自动恢复；
   - 人工干预次数；
   - 实际不可用时长。

无头模式的目标首先是“能否满足业务与恢复要求”，不是证明它必然优于 NapCat。

==================================================
七、稳定性观察
==================================================

短时功能通过不等于稳定。

每种进入稳定观察的模式，至少记录：

- 观察开始和结束时间；
- 总在线时长；
- 不可用时长；
- 人工扫码次数；
- 人工重启次数；
- KickedOffLine；
- 静默离线；
- WS 重连；
- action failed/unknown；
- 消息丢失、重复、乱序；
- 图片和大 payload 失败。

初始功能验证后，建议进行 24～72 小时观察。

如果当前执行会话无法完成长期观察：
- 留下可继续的监测方式和明确状态；
- 标记 SOAK_PENDING；
- 不得将短时间无故障写成“稳定性验证通过”。

NapCat 与 LLBot 不得同时登录同账号做所谓 A/B；采用顺序观察，并说明样本时长和环境差异。

==================================================
八、立即停止条件
==================================================

出现任一情况立即停止当前候选模式，保留日志，并按需回滚：

1. 用户个人 QQ 被退出、误杀或数据被修改。
2. 账号出现冻结、封禁、安全中心处罚或明确异常警告。
3. 测试机器人向非目标群或用户发消息。
4. 出现不可控重复发送。
5. 测试开始覆盖生产私聊历史或永久数据。
6. 同账号多端互踢且无法立即确认来源。
7. 连续快速登录失败，或反复要求人工扫码，继续试验可能加重账号风险。
8. 无法确认进程身份，无法安全停止候选协议端。
9. 备份或回滚路径失效。
10. 需要重新采用手工替换官方 QQ 文件才能继续。

停止后不要为了追求“测试完成”而绕过条件。

==================================================
九、回滚要求
==================================================

试验结束或中止后，根据用户需要恢复 NapCat 基线：

1. 只停止确认属于 LLBot/测试 QQ 的进程。
2. 确认 LLBot 不再持有机器人账号登录。
3. 恢复本轮实际修改过的配置，不盲目覆盖运行期间产生的新数据。
4. 启动现有 Python 服务与 NapCat，使用项目既有安全启动方式。
5. 验证：
   - 8080/8081；
   - get_login_info；
   - 测试群收发；
   - 私聊白名单收发；
   - RPC 回执；
   - 生产数据目录未变化或变化可解释。
6. 记录恢复后的账号与 WS 状态。
7. 回滚失败必须醒目标记，不得写“已恢复”。

==================================================
十、必须留下的总结
==================================================

在 qq_native_re/findings/llbot_trial/ 下留下：

1. REPORT.md
2. TEST_MATRIX.md
3. ROLLBACK.md
4. manifest.json（脱敏）
5. 必要的测试脚本与日志摘要
6. 如做了最小适配，附独立 patch 和适用原因

REPORT.md 至少包含：

- 测试目标与范围；
- 实际执行和未执行部分；
- LLBot、QQ、NapCat、Python 版本；
- 下载来源与文件哈希；
- 有头/无头配置差异；
- 备份位置；
- 修改文件清单；
- 测试矩阵及证据链接；
- 核心 API 兼容性；
- 两通道、历史、图片、回执、乱序、重复结果；
- 有头与无头的登录和恢复对比；
- 与 NapCat 基线的公平比较；
- 所有失败、阻塞和不确定项；
- 回滚验证结果；
- 最终判定：GO / CONDITIONAL_GO / NO_GO / INCONCLUSIVE；
- 若 NO_GO，明确是业务不兼容、登录不稳定、账号风险还是测试证据不足；
- 后续是否值得进入 Lagrange V2/Milky，不要自动扩大本轮范围。

结论纪律：

- PASS 必须有实际证据。
- 未运行写 NOT_RUN，不能写 PASS。
- 无法验证写 UNKNOWN。
- 不把 WS 在线等同于 QQ 在线。
- 不把短时间无掉线等同于长期稳定。
- 不把 LLBot 有头结果外推为无头结果。
- 不把个别社区 issue 当作本机必然故障。
- 不泄露密钥、登录凭据、完整私聊内容或个人 QQ 数据。

最后，在回复用户时用简洁中文说明：
1. 实际完成了哪些测试；
2. 有头与无头各自结论；
3. 是否已回滚及当前生产状态；
4. 报告和备份的准确路径；
5. 仍需用户人工完成的步骤。
